### 0.40.x push evidence: the supported surface

The pre-push gate accepts a full `test_run` as evidence only where holmes can check the run afterwards without changing your runner configuration. Outside that surface the push is refused as `environment`, with one message: "이 구성은 0.40.x가 증빙하지 않습니다 — 0.41 / 오너 결정". General support is planned for 0.41.

**A full run tests the commit, not your work tree.**
- It checks HEAD out as a temporary git worktree **outside the repository**, in `<os tmp>/holmes-headwt-<user>/<repository key>/<id>/`, made with no git hooks and no write to your git configuration. It links your gitignored `node_modules`, runs `ax.config.json` `testRun.prepare` there if you declare one (for example `["npm", "run", "build"]`; nothing is guessed, and a package-manager install is refused because `node_modules` is your work tree's; `[]` or `null` declares none, and any other malformed value ends the run with the reason *(0.41.1)*), runs the suite within the run's time budget, and removes the worktree. The prepare and the tests are told that worktree as `CLAUDE_PROJECT_DIR` *(0.41.1)*.
- holmes removes only a worktree git lists at that exact path, through `git worktree remove`; it never deletes a directory itself and never runs `git worktree prune`. A leftover of a run whose process is gone is removed by the next run.
- Untracked, ignored, modified, assume-unchanged and skip-worktree files never reach the run, so a red commit cannot pass on a green work tree. Nothing is written inside your repository, and nothing has to be added to `.gitignore`.
- **The run must read only HEAD, judged by what it loaded.**
  - A symbolic link anywhere in a linked `node_modules` that resolves into your work tree (a workspace package, at any depth) is `environment`, naming the link.
  - Before any test, the pytest interpreter is started in HEAD's worktree (`python -P`, so 3.11 or later) and asked where every dotted module name of HEAD's python files resolves (every layout and namespace package; capped by `testRun.pythonNames`, default 20000). An import-path entry or a `NODE_PATH` entry inside your work tree is `environment` by itself. A name that resolves into your work tree is `environment`, naming it, whatever the tests later do: subprocesses, xdist workers, a `sys.modules` restore. Typical causes are an editable install, a `.pth` finder or `PYTHONPATH`.
  - pytest also runs with a holmes plugin that records every module it loaded, judged the same way. The exempt locations are the interpreter's own library directories.
  - node is asked the same question for HEAD's package names, `NODE_PATH` included. The `node_modules` walk is bounded by `ax.config.json` `testRun.linkWalk` (`{ "entries": 500000, "seconds": 20 }` by default), and a directory it cannot read is `environment`.
  - Named limits:
    - a HEAD conftest that rewrites the plugin's record (a forgery; the environment question still holds);
    - a package that requires your work tree by absolute path;
    - a legacy sparse checkout (`core.sparseCheckout` in the shared config) keeps the worktree sparse, since turning it off would write your shared git configuration;
    - a JavaScript workspace monorepo whose `node_modules` links into the work tree, and a `NODE_PATH` entry inside the work tree, are refused as `environment`;
    - the environment question imports HEAD's packages to find their submodules, so a package `__init__` runs during it;
    - xdist is judged by the environment question; no xdist run was measured.
  - After upgrading to 0.40.1, run `test_run({ root, full: true })` once at the commit you push: records of 0.40.0 and scoped runs are no longer push evidence. A pytest project needs python 3.11 or later.
  - pytest reads HEAD's own configuration file, pinned with `-c`.
  - `PYTEST_ADDOPTS` and `PYTEST_PLUGINS` are dropped.
  - `GOFLAGS` with `-run` or `-skip` (also `-test.run`, and also set through `go env -w`) is `environment`.
- The pytest interpreter is still the work tree's (a `.venv` is not in HEAD).
- A scoped run stays in the work tree.

| Runner | Evidenced in 0.40.x | Refused as `environment` |
|---|---|---|
| jest | One jest configuration source (the root's, or one directory's) with one project. holmes passes jest no ignore argument. Passed means exit 0 **and** no failure in the report. | `projects`; jest tests at the root beside another directory's configuration, or two configurations; a package.json script that runs jest with `--config`/`-c`; a configured `testNamePattern`; output `--showConfig` cannot print |
| pytest | Default test names (`test_*.py`, `*_test.py`), outside pytest's default norecursedirs. `--rootdir` and `--confcutdir` are the unit, and `--ignore` adds your exclusions. Passed means exit 0 **and** no JUnit failure or error. | a declared `python_files`, `python_functions` or `python_classes`; `-k`/`-m` in `addopts` |
| go | The `_test.go` files `go list` builds on this platform with no tags, per package. Passed means exit 0 **and** no failed test event. Files go does not build here are named in `notBuilt`. | go test files under no `go.mod` |
| cargo, maven/gradle, dotnet | — | a build root holding tests or code; test files of those languages under no build root |
| others | — | a build file 0.40.x has no runner for (Gemfile, composer.json, Package.swift, build.sbt, mix.exs, CMakeLists.txt, pubspec.yaml) |

- **Exclusions** (`.gitignore`, `ax.config.json` `testRun.excludeDirs`, git submodules) differ by runner:
  - pytest takes them as `--ignore`, and go leaves those packages out;
  - jest is told nothing, and the tests it reports under an excluded tree leave the judgement. If such a test ran red, the push is `environment`, naming the file: the runner's own configuration must leave it out too;
  - a git submodule is empty in HEAD's worktree, and named.
- **Code** is tested only by an executed test of the scanned universe whose own nearest build root is the code's. That a unit ran is not evidence, and a test outside the repository credits nothing.
- **A push without evidence** is allowed only when there is nothing to test: no test file and no implementation code.
- **C# (dotnet) scoped verdict:**
  - It needs the JunitXml.TestLogger package; without it the run is `environment`.
  - A C# failure is held as red-error, because the JUnit report does not tell an assertion from an exception.
  - Each planned file must show an executed case. The report keys a C# case by its `file` attribute relative to the run directory, or by class namespace (classname) when it has none, so a namespace that differs from the path reads as not executed.
  - A TRX reader is a follow-up to measure, not a known fix.
- **Named limits:** a red behind a go build tag; a `-k` deselection that is not declared in configuration; a linked `node_modules` that differs from the lockfile.

## 🕵️ Philosophy & Vision: Beyond Code Generation

**Holmes-Kit** is not merely an AI code generator. Inspired by **Sherlock Holmes**, Holmes-Kit is built to **deduce, track down, and analyze code defects, structural drift, and security vulnerabilities** across the full Software Development Life Cycle (**SDLC**).

### 🛡️ Currently Supported Features (Production Features)
- **Stop judges the branch you are on; push judges every branch** *(new in 0.41.6)*: Stop's spec seam lists only the spec commits HEAD reaches that no recorded tip explains, so a spec commit granted in another worktree, or one on a fetched branch or tag, no longer raises ART-5 here. The push judgement still reads every branch and tag, so such a commit is judged when it leaves. A baseline advances HEAD's tip and keeps the others (at most 256; past that, tips another tip reaches go first). Tips are recorded as commit ids (an annotated tag is peeled).
- **`test_run` says what it recorded** *(new in 0.41.6)*: a full run that is not push evidence (red, stopped at its budget) answers `scopedEvidenceRecorded: false` and `attemptRecorded { judged, reason }` instead of `scopedEvidenceRecorded: true`; what it records and voids is unchanged. A `test_run` given a `head` refuses before it runs or records anything when the work tree differs from that head in a file of the range.
- **`node:test` files run under node's own runner** *(new in 0.41.6)*: `test_run` detects `node:test` files, runs them with `node --test` and judges them by structure, not as jest; the evidence names the runner `node-test`.
- **A principle-7 spec named with Windows separators is a person's seal** *(new in 0.41.6 — gate fix)*: a Files to Touch that writes a gate file as `src\holmes\hooks\stop.ts`, or names `src`, now puts the spec in the category a person seals; before, a full profile could seal it alone. The autonomous principle-7 seal after two clean reviews is built but ships **off** in 0.41.6 (`P7_AUTONOMOUS_SEAL_ENABLED = false`): a hard-link path is still open, so a person seals those specs as before.
- **A deletion naming many absent entries next to wiring is refused** *(new in 0.41.6 — gate fix)*: a deletion judgement reads each parent directory once and looks up at most 512 alias candidates; a command over that budget is refused instead of being judged slowly. A directory that no longer exists counts as absent.
- **Under auto mode, a sealed spec is staged without a person** *(new in 0.41.6)*: with autonomous approval on and no full profile, staging a sealed spec follows the same machine conditions as under a full profile. A spec that changes the owner ceiling or the decision core still goes to a person's form.
- **Nested Windows shells are read, or refused when they cannot be** *(new in 0.41.5 — gate fix, upgrade recommended)*: text handed to `cmd`, PowerShell or `wsl` (`cmd //c`, `start`, stdin, `Start-Process`, `wsl sh -c`) is judged as the shell it runs in, with 8.3 short names and `\\?\` spellings resolved to the protected file they name. What the gate cannot model there — cmd grammar, stdin, a run-time link, a program named by a variable, an interpreter under a program the gate does not read, an unknown copy switch — is refused as unjudgeable, and a shell write to a UNC or device path is refused. The gate is not a sandbox: where execution must be isolated, use the operating system's.
- **Stop finishes inside half of its harness's limit** *(new in 0.41.5)*: the budget is 30 s on Claude Code and Antigravity and 37.5 s on Codex. Judgement always runs; an observability stage that would cross the budget is skipped with a `not judged: budget` warning, and the next Stop runs it first. A cold scan cache is built in the background.
- **The spec seam judges past 200 new commits** *(new in 0.41.5)*: up to 5,000 in one `git log` pass, so a large clone no longer needs a person to re-baseline it. A fresh clone trusts its fetched merge-base, and forging a remote-tracking ref is refused.
- **Autonomous approval friction removed** *(new in 0.41.4 — a loosening, owner directive)*: a person's seal of an A-SPEC opens its principle-7 write window for **48 hours** instead of 12 (`autonomy.sealWindowHours` still only shortens it); `spec_approve` admits a REQ whose server-issued, unspent `triage_evidence` it spends at approval; the spec seam, past 200 new commits, rebaselines when every tip's spec-store tree equals a recorded tip's (`seam rebaselined`); and `spec_unseal` takes an optional `directive` that, under an active full profile, unseals a spec outside principle 7 without a grant, recorded with `full-autonomy:<scope>` as actor. Principle 7, config, secrets and approvals writes, the push and publish flags and spec deletion stay with a person.

Where that workflow runs, a `--no-verify` push or a hook-less clone shows as a failed run; it detects, it does not prevent, and write access can change or cancel it.
  - **What a full run runs.** HEAD, checked out in a temporary worktree outside the repository (see the top of this README). The files are what git sees there minus `ax.config.json` `testRun.excludeDirs`. A tracked file stays in even under a later ignore pattern. The record carries `ranIn: head-worktree` and the times of creation, preparation and run; the push gate accepts no full record without that marker.
    - Every execution unit runs with its own directory as cwd.
    - The supported surface is the table at the top of this README; everything outside it is refused as `environment`.
    - The jest unit is the root, or the one directory with its own jest configuration (a `jest.config.*` or package.json `jest` field). pytest units are the root and each directory with pytest configuration (`pytest.ini`, pyproject `[tool.pytest…]`, setup.cfg `[tool:pytest]`, tox.ini `[pytest]`); a parent skips its configured children.
    - A go unit is each `go.mod` holding go code.
    - Holmes never replaces your runner configuration. jest gets no ignore argument; pytest gets `--ignore` (it adds to your configuration) and `--rootdir=<unit>`.
    - Runner output is read from jest's `--outputFile` report or from well-shaped JSON only, so your own console output cannot break it. An output that cannot be read is refused as `environment`, never replaced by a default.
    - A git submodule is always outside the evidence and named in `notDetected`. A sparse work tree does not matter: HEAD's worktree is a whole checkout.
  - **What is checked after the run.** Every detected test must have run, at the granularity its runner reports: jest and pytest per file, go per package. Every build root holding code must have an executed test whose own nearest build root is that root: neither a nested package's tests nor a unit having run stands for its parent's code.
    - The expected tests are named by default naming only (jest's testMatch, pytest's `test_*.py` / `*_test.py`, go's `_test.go`). A runner rule that narrows collection, such as pytest `testpaths`, never removes one, so a test it leaves unrun is refused as `collect`.
    - go: a package whose tests all skip counts as run; a `_test.go` with no test function is named in `notTests`; test names are Unicode identifiers.
    - Named limits: a pytest `-k` deselection inside a file is below file granularity, and go build tags are below package granularity.
  - **What a refusal says.** It names one of four acts. It never recommends hiding a red test.
    - `fix-tests`: a red run, a unit that ran no test, code without tests in a build root, or code with no build file (it names the file to add);
    - `collect`: detected tests that did not run, named. Make the runner collect them, or exclude them if they are not the project's.
    - `rerun`: run the full call at the pushed head, pushing branches one at a time;
    - `environment`: the runner itself is missing, its output cannot be read, the configuration is outside the 0.40.x surface, an excluded tree's test ran red, a test outside the repository ran, HEAD's worktree could not be made or prepared (a run location that is a link or another user's, a failing or installing `testRun.prepare`, a linked work-tree package or import path), or the run stopped at the 180-minute ceiling (split the suite or ask the owner).
  - **Nothing to test.** A repository with no test file and no implementation code (README, settings, docs, configuration files such as `*.config.*`, `conf.py`, `.eslintrc.*`, `setup.py`) pushes with a notice and a `{ts, head, reason: "no-tests"}` line in `.ax/ledger/no-evidence-pushes.jsonl`.
  - **Exclusions are yours.** `.gitignore` and `testRun.excludeDirs` keep a tree out of the universe. An ignored, uncommitted tree is not in HEAD's worktree at all. For a committed excluded tree, pytest and go do not run it; jest is told nothing, and its report of the tree leaves the judgement (a red there is `environment`).
    - An `excludeDirs` entry with a `/` is a root-relative path, so `test/fixtures/pyproj`, `./vendor` and `fixtures/` all start at the root. One without is a directory name at any depth (`pyproj`).
    - Absolute entries, entries that leave the root, and entries that name nothing are ignored and named in `excludeDirsIgnored`.
  - **pytest collection.** Every `test_*.py` / `*_test.py` outside pytest's default norecursedirs is expected; `testpaths` does not narrow the list, and a declared `python_files`, `python_functions`, `python_classes` or `-k`/`-m` in `addopts` is outside the 0.40.x surface. A `test_*.py` that holds no test function is not a test: it is named in `notTests` and never required.
  - **Limit.** If the evidence file and the ledger directory are both made read-only, a red run cannot replace an older green record. The answer names that failure in `recordFailed`.
- 🧪 **Self-healing & diagnostic doctor**: integrity checks that name the fix for each failing one (`doctor`), repair of the recovery skills (`holmes-kit skills refresh`) and of a blocked spec (`spec_remediate`), plus a live report of holmes-kit's own advertised MCP schema token cost.
- 🔢 **Sensible spec numbering** *(0.12.1)*: a brand-new project's first slice is **REQ-100**; existing projects keep `max(existing)+1` exactly, and 4-digit ids (including `ADR-1000+`) work cleanly.
- 🌐 **English CLI & hook surface** *(0.13.0)*: the operator-facing CLI, `doctor` output, hook `deny` reasons and interactive prompts are English, guarded by a hangul-absence test over the **rendered runtime output** rather than a source scan. Not yet English: a few strings outside that test (a truncation marker, one `init --dry-run` hint) and the comments in the files `init` writes for roles and `.gitattributes`; planned for 0.41.
- 🤖 **CLI-first AI harness matrix**: native process hook gating for Claude Code, Antigravity CLI (AGY), Codex CLI, and the Google Antigravity SDK.

## ⚡ Quickstart (3-Minute Setup)

### 1. Install — find your row first

The same wrong command was run three times by a real adopter before the right one; a table beats
prose read top-to-bottom.

**Windows (recommended)** — a bootstrap installer that runs *before* npm and fixes what npm cannot: it relocates out of protected folders (an elevated PowerShell opens in `C:\WINDOWS\System32`, where `npm install` fails with `EPERM`), checks the Node.js version, and, if a native module fails to build, prints the one `winget` command that installs the missing C++ toolchain instead of raw compiler output. Pure Windows PowerShell 5.1; no prompts; nothing persistent is changed.
```powershell
# From a downloaded copy of the package (e.g. after `npm pack`, or from a checkout):
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\install.ps1

# One-liner (once hosted):
# irm https://<host>/install.ps1 | iex
```
Add `-DryRun` to see what it would do without installing. Exit codes: `0` ok / already installed · `2` bad argument · `3` Node.js too old · `4` npm failed (remediation printed) · `5` installed but not on `PATH` (prefix printed).

| Which situation are you in? | Privileges | Command |
|---|---|---|
| **Using it in one project** (most people) | none | `npm install --save-dev @holmes-lab/holmes-kit` |
| **Zero-install one-shot** (to look at it, not to keep) | none | `npx -y @holmes-lab/holmes-kit init` — npx fetches and runs; read "How the MCP server is wired" below before keeping this wiring |
| Company-managed PC / restricted account | none | same — no system directory is touched |
| CI / container | none | same, plus `--prefer-online` right after a release |
| CLI across many projects (`-g`) | depends | run `npm config get prefix` first — see below |

**How the MCP server is wired** *(0.31.0)*: from an install (`--save-dev` or `-g`), `init` wires every
harness as `node <install>/bin/holmes-mcp.js`. A zero-install `npx` run has no lasting path, so it is
wired through `npx` — and npx runs npm in each session workspace, whose `.npmrc` (`node-options`,
registry) and `node_modules` can replace the Holmes server. `init` and `doctor` say so; install, then
re-run `holmes-kit init --force`.

**Stale global shadowing** *(field-measured on Windows, 2026-08-31)*: an old global install makes the
bare `holmes-kit` command run the OLD version while `npx holmes-kit` runs the local one — and
Windows has TWO global roots (`C:\Program Files\nodejs` and `%APPDATA%\npm`), so `npm uninstall -g`
against one root can leave a live shim in the other. If `holmes-kit --version` and
`npx holmes-kit --version` disagree, run `where.exe holmes-kit` (Windows) / `which -a holmes-kit`
and remove the stale shim; prefer the `npx` form day-to-day.

**Before `npm install -g`**: if `npm config get prefix` names a protected directory
(`C:\Program Files\nodejs`, `/usr/local`), `-g` dies with `EPERM` **before any package file
arrives** — no package version can fix that, and elevation is the wrong fix (it runs native
install scripts with system privileges, and it did not even work in the reported case). Move the
prefix to user space instead — one-time setup, exact commands in the
**[Install Guide](docs/install-guide.md)**, along with troubleshooting keyed to the exact error
text (`EPERM mkdir`, `notarget`, `better-sqlite3` build failures).

**Prerequisites** — Node.js `>= 20.0.0`. The 8 tree-sitter grammars ship prebuilt binaries for
macOS/Linux/Windows and compile nothing; `better-sqlite3` downloads a prebuild at install time,
falling back to compiling — only that fallback needs a C++ toolchain (VS Build Tools / Xcode CLT /
`apk add python3 make g++`). **npm 12 skips dependency install scripts that `allowScripts` does not
cover.** npm's docs say a global install has "no project `package.json` to write to" and point to the
install-time `--allow-scripts` flag or a user-level setting; the 0.41.2 field install was blocked with
`allowScripts` present. So after `npm install -g` the driver may never be built and every graph tool fails
("Could not locate the bindings file"). Rebuild it, then restart the MCP server:
- global install: `npm rebuild -g better-sqlite3 --foreground-scripts --allow-scripts=better-sqlite3`
  (installed with a prefix, `npm i -g --prefix P`? `holmes-kit doctor` prints the exact command — it alone names `--prefix`, and a path with a space or shell character appears as `<PREFIX>` with the path on its own line)
  (or install with `npm install -g @holmes-lab/holmes-kit --allow-scripts=better-sqlite3`, or persist it
  with `npm config set allow-scripts=better-sqlite3 --location=user`);
- project install: `npm install-scripts approve better-sqlite3`, then
  `npm rebuild better-sqlite3 --foreground-scripts` (npm refuses `--allow-scripts` on a project rebuild).

On Windows use `npm.cmd`, and run the two project commands as two lines (PowerShell 5.1 does not accept
`&&`). If the driver cannot be rebuilt on a machine (no rights over the global prefix), the owner can set
`guardrail.preEditEvidence` in `ax.config.json` to `warn` until it is; an agent cannot change that setting
(it is the owner's, *new in 0.41.3*), and the texts an agent reads only tell it to ask the owner. `holmes-kit doctor` and `workspace_preflight` (check `native-driver`) report the cause, which differs
for a Node upgrade (rebuild for the new Node) and a binary from another platform *(new in 0.41.3)*.

### 2. Initialize in Your Project
```bash
cd /path/to/your/project
npx holmes-kit init      # drop the npx prefix if you installed with -g
```
*An interactive prompt will ask which AI agent harnesses to wire into your project:*
```text
? Select the AI Agent harnesses to wire into this project:
  [X] 🤖 Claude Code          (.claude/settings.local.json, .mcp.json)
  [X] 🚀 Antigravity CLI (AGY) (.agents/mcp_config.json, hooks.json, skills)
  [ ] 💻 Codex CLI            (~/.codex/config.toml)
```
*It then asks — defaulting to **No** — whether to grant **autonomous spec approval** (low-risk specs
self-seal; governance-critical, high-risk and irreversible ones ask for an approval — which, as the
Known limitations say, the same user's agent shell can forge). Skip the prompt with
`--autonomy` / `--no-autonomy`, or turn it on later per-session with `holmes-kit autonomy on`.*

### 3. Verify Health
```bash
npx holmes-kit doctor
```
*If everything is green, your project is governed and ready for AI pair-programming!*

### 4. Local semantic layer by default; cloud remains optional

During a normal npm installation, Holmes-Kit prepares the public pinned BGE-M3 assets in a shared
user cache and enables tier **`local`** only after a real offline inference check succeeds. Local
inference has **zero repository-text egress**. BM25, citation, and graph search remain available
whether preparation succeeds or not. The optional cloud tier raises recall further on requests
your vocabulary cannot reach (measured on 305 traceability cases — see the feature list above):

**Tier `local` — no egress, no account.** The embedding runtime ships with holmes-kit. Package
installation attempts setup once by default; run these commands later to retry or prove readiness:
```bash
npx holmes-kit semantic-setup    # downloads the public bge-m3 assets once, shared across projects
npx holmes-kit semantic-check    # verifies OFFLINE inference — a real 1024-dim normalized vector
npx holmes-kit doctor            # → semantic tier: local (no egress)
```
`HOLMES_SKIP_MODEL_INSTALL=1` explicitly declines automatic preparation. It never blocks an
explicit `semantic-setup` or `semantic-check`. Models live in `~/.holmes/models`
(`%USERPROFILE%\.holmes\models` on Windows); `HOLMES_MODEL_CACHE` overrides that, including for a
prepopulated offline cache. A cache activates the local tier only after successful offline inference
writes a current readiness receipt. If lifecycle scripts are blocked, the download fails, or the
cache is unverified or changed, the package remains usable: `doctor` reports **unavailable** or
**degraded** and names `semantic-setup` as the recovery command. A runtime or nonempty directory is
never treated as a working embedding tier.

> **Security note.** This package's dependency chain pulls `protobufjs@6.x` through
> `@xenova/transformers → onnxruntime-web → onnx-proto`, which carries a critical advisory. npm's
> `overrides` is a ROOT-manifest field, so we cannot fix this on your behalf — declare it in YOUR
> `package.json` to resolve it:
> ```json
> { "overrides": { "protobufjs": "^7.6.3" } }
> ```
> Measured from a fresh install: `critical 1 → 0`, `high 5 → 3`, with local inference intact.

> On **ARM Linux**, install with Node 20 or 22: `tree-sitter@0.21.1` ships no `linux-arm64` prebuild,
> so it compiles from source, and that compile fails against Node 24 headers. The failure happens
> while npm is still installing dependencies — before Holmes-Kit exists — so `doctor` cannot diagnose
> it. On x64 the prebuild is used and Node 24 is fine.

**Tier `cloud` — highest recall, explicit consent (`gemini-embedding-001`).** Setting a key IS
the consent act: with a key present, repository-derived text is sent to Google's embedding API.

1. Get a Gemini API key (Google AI Studio → <https://aistudio.google.com/apikey>; the free tier
   is enough to try it).
2. Store it **outside your project tree** with the built-in command — the key rides **stdin,
   never argv**, lands in `~/.holmes/credentials.json` with `0600` permissions, and no output
   ever contains the value:
   ```bash
   npx holmes-kit semantic-key set        # hidden prompt on a TTY; or:  echo "$KEY" | npx holmes-kit semantic-key set
   npx holmes-kit semantic-key status     # shows the key's SOURCE only, never the value
   npx holmes-kit doctor                  # → semantic tier: cloud (egress: on)
   ```
   On macOS the key prefers the system keychain; elsewhere the `0600` file is the store.
   Environment variables also work and take precedence (`HOLMES_SEMANTIC_API_KEY` dedicated, or
   the ecosystem-compatible `GEMINI_API_KEY` / `GOOGLE_API_KEY`) — useful for CI. Prefer
   `semantic-key set` on workstations: it keeps the key out of shell history, `.env` files, and
   the repository.
3. To revoke consent at any time:
   ```bash
   npx holmes-kit semantic-key unset      # clears the stored key; tier falls back to local/none
   ```

> 🔒 **Never** commit a key, pass it as a CLI argument, or put it in a file inside the project
> tree. Holmes-Kit's credential chain has **no project-tree source by design**, and agents are
> gated from setting keys on their own — consent is meant to stay a human act (the hook is no security boundary
> against the same user's agent shell — Known limitations).

## 🔄 Daily Workflow (How It Works)

Once initialized, your AI agent automatically follows the **No Spec, No Code** lifecycle:

```mermaid
flowchart LR
    A["1. Spec First<br/>(REQ → A-SPEC)"] --> B["2. Test First<br/>(TDD & T-SPEC)"]
    B --> C["3. Implementation<br/>(// @implements A-SPEC)"]
    C --> D["4. Verified Code<br/>(Provenance Sealed)"]
```

1. **Spec First**: The agent authors requirements and architecture specs via `spec_create`.
2. **Test First**: The agent writes tests and approves `T-SPEC` before writing implementation code.
3. **Implement**: Code files anchor to their architecture spec with `// @implements A-SPEC-NNN`.
4. **Deterministic Guard**: If the agent attempts to write code without approved specs in a form the gate recognises, **Holmes-Kit hooks block the action and provide exact next steps**.
